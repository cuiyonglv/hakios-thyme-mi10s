# 小米10S推进计划

更新：2026-11-03。原则：先完善和验证，再考虑持久刷写。
源码在`work/thyme-storage-bringup`分支按已检查的里程碑同步；CI只运行主机测试，
不自动生成安装许可或执行手机操作。详细通过标准见[ACCEPTANCE.md](ACCEPTANCE.md)。

## 每一步的检查点

| 检查点 | 操作范围 | 必须留下的证据 | 未通过时 |
| --- | --- | --- | --- |
| G1 构建一致性 | 只改电脑文件 | 干净提交、CI、输入/产物哈希；只读loader记录校验通过 | 不把旧产物混入测试包，回到源码修复 |
| G2 恢复保障 | 核实材料，再准备匹配的临时恢复环境 | 完整恢复文件校验、来源及版本；实际分区备份和哈希；返回原安卓的记录 | 不运行未知恢复镜像，不切槽、不改GPT |
| G3 有界临时启动 | 条件满足后才fastboot boot | 匹配thyme的DTB/UEFI/固件、具体镜像哈希、120秒上限、日志与退出路径 | 结束测试、回安卓，保留日志定位，不反复盲试 |
| G4 功能验收 | 逐组加入硬件，隔离测试数据 | 每项核心功能的日志、观察与重复测试；至少三轮持久化一致性 | 该功能保持未通过，不用其它机型结果代替 |
| G5 持久安装 | 仅在前面条件满足后准备 | 明确分区变化、每个写入范围、恢复材料、镜像哈希、失败回退方案 | 没有完整方案就继续保留安卓 |

G1提供了可执行校验，而不只是一份人工清单：

```sh
# 先提交并重新构建，identity输入必须是这次构建实际使用的本地文件。
THYME_REVISION=$(git rev-parse HEAD)
python3 scripts/verify-loader-build.py \
  --artifact src/loader/loader.efi --manifest src/loader/loader.build.json \
  --source-dir src/loader --identity /path/to/local/identity.h \
  --revision "$THYME_REVISION"
```

校验会拒绝可写/脏源码/提交不符的构建，校对源码、identity和产物哈希，并检查ARM64
EFI文件头。通过只表示这些输入一致，不验证发布者身份或本机硬件，不代表允许刷入。

## 阶段1：完成可核对的构建与布局（进行中）

### 当前执行顺序与停止条件

1. **先查生成工具，再修内核导出。** 当前实际构建依赖的`host/bin/iig`是替代脚本：
   复制SDK预生成头文件；有`iig-impl/<name>.iig.cpp`时复制实现，否则生成空翻译单元。
   已实查`IOService.iig.cpp`只有一行“no DriverKit implementation generated”注释。
   因此优先盘点各类生成实现是否完整、版本是否匹配，并核对同版本声明和RPC调用语义。
   这能解释部分包装缺口，但不能据此认定131项全部同源。不得将空文件或成功空桩当作完成。
   产物：生成器来源/版本/覆盖报告、缺口分类、完整make和原导出检查结果。
   已进一步实查：17个生成CPP中16个为空；唯一替代实现含44个返回
   `kIOReturnUnsupported`的占位方法和21个直接跳转包装。因此即使减少131项缺失，
   也不能仅凭链接成功宣布DriverKit可用；必须同时处理已有占位方法并复核直接跳转语义。
   [依赖审计记录](reports/iig-dependencies.json)包含输入哈希和占位符号列表。
   可重复扫描实际生成目录和替代实现目录：
   `python3 scripts/audit-iig-inputs.py --generated-dir <DriverKit生成目录> --replacement-dir <iig-impl目录> --out <报告.json>`。
   当前输入实测退出1并阻止通过；[逐文件报告](reports/iig-input-files.json)记录了18份输入。
   该工具只识别已知占位标记，未检出标记也不能代替ABI、完整构建和运行验证。
2. **独立推进恢复材料。** 官方包仍在分块下载，未完整校验前不能用于恢复；完成后再核对
   当前系统版本、包内引导文件和恢复方式。官方包不能代替本机独有分区备份。
3. **先设计版本化布局，再修持久化。** 现组合越界8,177,904字节；先明确各区域、容量、
   版本及兼容/拒绝策略，再同步修改构建器、loader和var_store。用稀疏临时文件验证边界、
   空间不足、截断、损坏槽和中断恢复；电脑文件通过后才考虑设备隔离测试区。
4. **最后准备临时启动。** 内核完整构建、匹配thyme硬件材料及G2恢复保障缺一不可。
   准备具体哈希、日志提取和退出步骤后进入G3；当前不刷写、不改GPT、不切槽。

每项只按证据标记“通过/未通过/待实机”。本地九组主机回归及提交
`4e02eb10308917e9315dd7ccf729a54f9cbfe642`的CI已通过；这不包含内核完整构建或手机功能验收。

| 工作 | 当前状态 | 完成条件 / 产物 |
| --- | --- | --- |
| 镜像边界、哈希、存储并发、损坏槽回退 | 主机回归和CI已通过 | 后续修改持续保持通过，记录测试覆盖不到的硬件行为 |
| 内核导出检查 | 已生成明确的缺失清单 | 分类处理真实缺失实现、受支持配置及导出声明；完整make成功，不能关闭检查或填成功空桩 |
| 统一镜像与保存区布局 | 待设计 | loader、kernel、var_store及构建器共享同一版本化布局；保留写入范围和分区身份校验 |
| 构建可复现性 | 已修正loader构建入口和LF换行 | 固定上游/SDK/工具链版本；输出提交、构建参数、文件哈希及验证结果清单 |
| 实际存储恢复路径 | 目前仅有主机模拟覆盖 | 增加完整保存/解包测试与阶段日志；明确恢复失败策略，避免半恢复后继续启动 |

当前内核审计使用实际构建的`nm -gj`符号表与七组通用/arm64导出声明：
22,578个已定义符号、5,638项声明，缺失131项：IOKit 89、Libkern 2、Private 5、
Private.arm64 35。其中91项的解码名称涉及IORPC/Invoke/Dispatch；这是分类线索，
不是“全部都是同一个问题”的结论。
已按原生工具的尾部`*`前缀匹配规则处理通配导出；将模式当作字面量会产生误报。
[原始清单与输入哈希](reports/kernel-exports.json)保留了每条声明的位置和解码结果。
规则来源为[同版本XNU的kextsymboltool](https://github.com/apple-oss-distributions/xnu/blob/c54f35ca767986246321eb901baf8f5ff7923f6a/SETUP/kextsymboltool/kextsymboltool.c)。

进一步分类发现34项缺失包装能在已定义符号中找到相应`_Impl`，例如
`IOService::CopyName_Impl`、`StringFromReturn_Impl`与`IOMemoryMap::_CopyState_Impl`。
它们只是候选对应关系，尚须核对函数签名、supermethod/RPC语义和调用方；
审计仍把缺失包装算作缺失，不将候选关系算为实现成功。

下一项具体工作：核对IIG生成代码与真实`_Impl`实现，分清DriverKit包装缺口和
Apple平台专用接口，不把`kIOReturnUnsupported`空桩当作已经实现功能。
审计工具为`scripts/audit-kernel-exports.py`，发现缺失时退出非零，不修改导出表。

当前基础镜像组合越过保存区起点8,177,904字节。不能仅在一个文件里挪动保存区。
新布局必须显式区分旧布局，测试升级/拒绝行为，保留旧数据回退能力。
本机的GPT位置、分区GUID和安卓槽位只能来自实测，不能照搬作者256GB机器的常量。

## 阶段2：建立恢复保障并取得本机硬件材料

顺序如下，任一必要项未完成，不进入手机启动实验：

1. 取得匹配当前安卓的完整官方恢复材料，校验下载内容；准备来源可核对的thyme恢复环境。
2. 临时运行匹配恢复环境，确认root只读访问；备份设备独有分区、当前安卓引导及实际GPT。
   恢复环境只允许读取，不能自动解密后修改文件系统、刷入自身、切槽或安装root。
3. 从本机提取DTB及所需GPU/WiFi等固件，核对芯片、供电、内存保留区和固件哈希。
4. 准备与本机匹配的UEFI，明确它的存储和日志写入路径；验证能可靠返回安卓。

已经尝试Fastboot只读`fetch boot_b`：设备返回不支持`max-fetch-size`/`fetch`。
随后立即重启回安卓；这不构成备份成功。ADB普通shell仍不能读取这些底层分区。
当前安卓在B槽，不执行示例中的`fastboot flash boot_b`。

## 阶段3：临时内存启动与功能验收

先生成关闭持久化、限制时长、可取日志的RAM启动包。需要逐条审核日志写入等路径，
不能只凭`ufs_write=0`称完全不写闪存。loader当前默认编译为
`THYME_STORAGE_WRITES=0`：自身的logdump、darwin和misc直接块写入均被拒绝，
日志保留在RAM供USB读取；UEFI内部和内核独立写入路径仍需另行核查。
每个测试记录源码提交、镜像哈希、启动参数、
日志和观察结果。一次只增加一组硬件，保持可返回安卓。

顺序：

1. 基本内核/内存/文件系统、超时退出和日志。
2. 桌面、显示、触摸、多点和手势、实体按键。
3. GPU渲染、帧率、温度、退出后再次启动。
4. WiFi关联、DHCP、DNS、HTTPS、断线和休眠恢复。
5. 电池、真实充电、插拔电源；音频播放、麦克风与回放。
6. 在隔离测试区验证保存/重启/恢复、至少三轮设置/文件一致性与损坏槽回退。

相机、蓝牙、通话/SMS/移动数据、第三方应用单独列结果。需要这些功能时，必须继续
完成相应验收；不能用“其它七项已过”推断它们可用。

## 阶段4：持久安装与回退验证

前面阶段全部满足必要条件后，才生成持久安装方案：实际分区变化、写入范围、镜像
哈希、备份、回退命令和故障处理都要明确。先验证失败回退，再写入，最后做多轮
冷启动、长时间运行和数据恢复检查。没有满足目标就继续保留安卓。
